Enterprise Identity & Access Flow: Authentication & Authorization

How Microsoft Entra ID acts as a centralized identity provider for enterprise environments — issuing SAML assertions, OIDC tokens, and OAuth 2.0 access tokens to enable single sign-on, application authentication, delegated API access, and secure service-to-service communication.

Overview: The Identity Triangle

Enterprise identity flows involve three parties:

Party 1
Users (Employees)
Human users who need access to AWS accounts, web applications, or APIs. They authenticate with passwords, MFA, and conditional access policies.
Party 2
Microsoft Entra ID (Identity Provider)
The centralized identity provider that authenticates users, manages groups/directories, enforces policies (MFA, conditional access), and issues tokens/assertions to relying parties.
Party 3
Relying Parties (Service Providers)
AWS IAM Identity Center, web/mobile applications, and APIs (Microsoft Graph, Salesforce, internal services) that trust Entra ID to verify identity and grant access.

Authentication vs Authorization

Authentication proves who the user is (identity verification). Authorization determines what the user or application is allowed to do (permission granting). SAML and OIDC handle authentication. OAuth 2.0 handles authorization. In practice, these often work together in a single flow.

Flow 1: AWS Console SSO (SAML)

Purpose: Authenticate a user and provide access to AWS accounts via single sign-on.

  • 1. User opens AWS Console
    SP-Initiated flow — user navigates to the AWS sign-in page.
  • 2. Redirect to Entra ID
    AWS redirects the user to Entra ID for authentication.
  • 3. Entra ID authenticates user
    User provides credentials. Entra ID enforces MFA and conditional access policies.
  • 4. SAML Assertion issued
    Entra ID sends back a SAML Assertion containing: user identity (e.g., alice@company.com), groups (e.g., CloudAdmins), attributes, and role mapping.
  • 5. AWS IAM Identity Center validates
    IAM Identity Center validates the assertion and assigns the user to the appropriate IAM role.
  • 6. User accesses AWS accounts
    User assumes IAM roles in target accounts (Dev / Prod / Security) based on group membership.
SAML Assertion Contains

User Identity (e.g., alice@company.com) · Groups (e.g., CloudAdmins) · Attributes for role mapping · Signature from Entra ID for validation

Flow 2: Application Login (OIDC)

Purpose: Identify the user (authentication) for a web or mobile application.

  • 1. User opens application
    User navigates to a web or mobile application hosted on AWS or elsewhere.
  • 2. Redirect to Entra ID (OIDC)
    Application redirects to Entra ID's authorization endpoint with an OIDC request.
  • 3. Entra ID authenticates user
    User authenticates with MFA and policies applied.
  • 4. ID Token returned (JWT)
    Entra ID returns an ID Token to the application containing: user identity (sub), name, email, groups/roles, and other claims.
  • 5. Application validates token
    Application verifies the JWT signature, issuer, audience, and expiration — then establishes a session for the user.
ID Token Contains

User Identity (sub) · Name, Email · Groups / Roles · Other Claims · Signature · Expiration

Flow 3: API Access (OAuth 2.0 — Delegated)

Purpose: Authorize an application to access APIs on behalf of the user.

  • 1. User authenticated in application
    User is already logged into the application (via OIDC flow above).
  • 2. Application requests access token
    Application requests an access token from Entra ID on behalf of the user, specifying the target API and required scopes.
  • 3. Entra ID returns Access Token (JWT)
    Entra ID validates the request and returns an access token with scoped permissions (e.g., Mail.Read).
  • 4. Application calls API with token
    Application includes the access token in API requests (Authorization: Bearer header).
  • 5. API validates token and checks permissions
    The resource server (e.g., Microsoft Graph) validates the token signature, checks scopes and roles, and returns the requested data.
Access Token Contains

Scopes / Permissions (e.g., Mail.Read) · Audience (API) · User or App ID · Expiration · Issuer signature

Flow 4: Service-to-Service (OAuth 2.0 — Client Credentials)

Purpose: Authorize a service or application to access APIs without a user — machine-to-machine communication.

  • 1. AWS Service requests token
    A Lambda function, ECS task, or background service requests a token using Client Credentials (client ID + secret or certificate). No user is involved.
  • 2. Entra ID returns Access Token
    Entra ID authenticates the application (not a user) and returns an access token with app-level permissions.
  • 3. Service calls API with token
    The service uses the access token to call internal or external APIs.
  • 4. API validates token and checks app permissions
    The resource server validates the token and checks application roles/permissions (not user scopes).
Client Credentials Access Token Contains

App (client) Identity (e.g., employee-sync-service) · Roles / Permissions (e.g., HR.Read) · Audience (API) · Expiration · No user identity — this is purely application authorization

Key Concepts

Concept
Authentication
Proves who the user is. Handled by SAML assertions and OIDC ID tokens. The identity provider (Entra ID) verifies credentials and issues proof of identity.
Concept
Authorization
Determines what the user or application is allowed to do. Handled by OAuth 2.0 access tokens with scopes and roles. The resource server enforces permissions.
Concept
Token
A digital credential (JWT) issued by Entra ID. Contains claims about the user or application — identity, permissions, audience, expiration. Cryptographically signed for tamper detection.
Concept
Assertion
A SAML statement issued by Entra ID — an XML document containing identity claims, group memberships, and attributes. Used specifically for SSO with legacy and enterprise service providers.
Concept
Role / Scope
A permission to perform an action on a resource. Scopes are delegated (user-consented, e.g., Mail.Read). Roles are application-level (admin-assigned, e.g., HR.ReadWrite.All).
Concept
Conditional Access
Policies in Entra ID that enforce conditions before granting access — require MFA, block risky sign-ins, restrict by location/device, or require compliant devices.

JWT: The Token Format That Powers Everything

JSON Web Token (JWT) is the standard format for OIDC ID Tokens and OAuth 2.0 Access Tokens. Understanding JWT is essential because it's the actual credential that moves between systems.

JWT Structure: Three Parts

eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.SflKxwRJSMeKKF2QT4fwpM...
Part 1
Header
Specifies the token type (JWT) and signing algorithm (RS256, ES256). Tells the relying party how to verify the signature.
Part 2
Payload (Claims)
The actual data — who the user is (sub), what they can do (scope/roles), who issued it (iss), who it's for (aud), and when it expires (exp). This is the identity/authorization information.
Part 3
Signature
Cryptographic signature created with the issuer's private key. The relying party verifies it using the issuer's public key — proving the token hasn't been tampered with and was issued by a trusted authority.

Where JWT Plays a Role

Flow JWT Token Type What It Contains Who Validates It
Application Login (OIDC) ID Token User identity, name, email, groups The application
Delegated API Access Access Token Scopes (e.g., Mail.Read), audience, user ID The API / resource server
Service-to-Service Access Token App identity, roles, audience (no user) The API / resource server
AWS Console SSO Not JWT — uses SAML Assertion (XML) User identity, groups, attributes AWS IAM Identity Center
Why JWT Matters

JWTs are self-contained — the relying party can validate them without calling back to the identity provider. This makes them fast (no network round-trip for validation), scalable (no session state on the server), and portable (any service with the public key can verify them). The tradeoff: they can't be revoked until they expire.

Cloudflare Access Tokens: Zero Trust at the Edge

Cloudflare Access adds another layer to the identity flow — acting as a reverse proxy that enforces authentication at the network edge before traffic ever reaches your application.

How It Works

  • 1. User requests application URL
    Request hits Cloudflare's edge network first — before reaching the origin server.
  • 2. Cloudflare redirects to identity provider
    If no valid session exists, Cloudflare redirects the user to the configured IdP (Entra ID, Okta, Google, etc.) for authentication.
  • 3. IdP authenticates and returns token
    Entra ID (or other IdP) authenticates the user and returns a token to Cloudflare.
  • 4. Cloudflare issues CF Access JWT
    Cloudflare validates the IdP token and issues its own signed JWT (the "CF Authorization" token) as a cookie. This token contains the user's identity and policy decision.
  • 5. Request forwarded to application
    Cloudflare forwards the request to the origin with the CF Access JWT in a header (Cf-Access-Jwt-Assertion). The application can validate this JWT to identify the user without implementing its own authentication.
Cloudflare Access JWT Contains

User email · Identity provider used · Audience (the Access application ID) · Issued-at and expiration times · Custom claims from access policies · Signed by Cloudflare's team-specific key (verifiable via /cdn-cgi/access/certs endpoint)

Where Cloudflare Fits in the Stack

Benefit
Zero Trust: Authenticate Before Reaching Origin
Applications don't need to be publicly exposed. Cloudflare blocks unauthenticated requests at the edge — the application only receives pre-authenticated traffic with a verified JWT.
Benefit
IdP-Agnostic Authentication Layer
Cloudflare Access works with any OIDC-compliant IdP (Entra ID, Okta, Google, GitHub, etc.). Applications validate one token format (CF JWT) regardless of which IdP authenticated the user.

The Big Picture: Everything Maps to a Question

The entire enterprise identity stack answers five fundamental questions:

Question Answer Mechanism
Who are you? Authentication Entra ID + SAML / OIDC
What are you allowed to do? Authorization OAuth 2.0 Access Tokens (scopes & roles)
Should an account exist? Provisioning SCIM (automated user/group lifecycle)
How do you access AWS? AWS Access SAML Federation → IAM Identity Center → IAM Roles
Is the request trustworthy? Zero Trust (edge) Cloudflare Access → JWT at the edge

Protocol-to-Purpose Mapping

SAML
AWS Access = SAML Federation
SAML Assertion → IAM Identity Center → IAM Roles. The user authenticates once and gets federated access to multiple AWS accounts based on group membership.
OIDC
Application Login = OIDC ID Tokens
The application learns who the user is via a signed JWT. No password stored in the application — identity is delegated to the trusted provider.
OAuth 2.0
API Access = OAuth Access Tokens
Applications call APIs with scoped access tokens — either on behalf of a user (delegated) or as a service (client credentials). Least-privilege by design.
SCIM
Provisioning = Automated Lifecycle
When a user joins or leaves the organization in Entra ID, SCIM automatically creates, updates, or deactivates their accounts in downstream applications — no manual provisioning.

Key Benefits

Benefit
Single Sign-On (SSO)
One authentication event grants access to all enterprise applications and AWS accounts. Users authenticate once with Entra ID and access everything without re-entering credentials.
Benefit
Centralized Security Policies
MFA, conditional access, and risk-based authentication are enforced at the identity provider level — not per-application. One policy change applies everywhere.
Benefit
Fine-Grained Authorization
OAuth scopes enable least-privilege access — applications request only the permissions they need. No over-provisioning of credentials.
Benefit
Secure Service-to-Service
Machine-to-machine communication uses short-lived tokens instead of stored user credentials. No passwords in config files. Tokens expire automatically.
