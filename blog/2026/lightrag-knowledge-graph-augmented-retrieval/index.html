Knowledge-Graph-Augmented RAG: How LightRAG Bridges Flat Retrieval and Structured Reasoning

Standard vector RAG retrieves text chunks by similarity — and hopes the LLM figures out the connections. LightRAG introduces a structured knowledge graph into the retrieval process, enabling multi-hop reasoning, entity-centric lookups, and dual-level retrieval that pure chunk similarity cannot achieve.

The Problem with Flat RAG

Standard vector RAG has a fundamental limitation: it represents documents as flat collections of chunks. Each chunk is embedded independently, and retrieval finds the top-K most similar chunks to the query. This works for simple factual questions but fails when:

Failure
Complex Inter-Dependencies
Information about how entities relate to each other is spread across multiple chunks. A flat search finds individual mentions but misses the relationships connecting them.
Failure
Multi-Hop Reasoning
Questions requiring traversal of relationships (A depends on B, B conflicts with C) cannot be answered by similarity search alone — the answer requires following a chain of connections.
Failure
Thematic Understanding
High-level questions about trends, patterns, or overarching themes require aggregating information across many documents — not just finding the most similar chunk.
The Core Issue

Flat data representation leads to fragmented answers and fails to capture complex inter-dependencies. The retrieval system has no understanding of structure — it only knows "this text is similar to that text."

What is LightRAG?

LightRAG is a retrieval-augmented generation framework that augments standard vector-based RAG with an automatically constructed knowledge graph. During ingestion, it extracts typed entities and binary relationships from your documents using an LLM, building a structured graph alongside the traditional vector index.

At query time, it performs dual-level retrieval — searching both the entity graph (for precise, local lookups) and the relationship graph (for thematic, global reasoning) — then merges results with relevant source chunks to provide comprehensive, context-rich answers.

Key Insight

LightRAG doesn't replace vector search — it augments it with graph structure. You get the semantic coverage of vector similarity PLUS the precision of explicit entity relationships. The graph tells you what's connected to what; the vectors tell you what's semantically relevant.

Ingestion Pipeline

The ingestion process transforms raw documents into a dual representation: a knowledge graph AND a vector index, both built from the same source material.

  • 1. Chunking
    Documents are split into token-sized chunks using a configurable tokenizer (default chunk size: ~1200 tokens, overlap: ~100 tokens).
  • 2. Entity & Relationship Extraction
    Each chunk is sent to an LLM with a structured prompt instructing it to extract typed entities (name, type, description) and binary relationships (source, target, keywords, description). Supports "gleaning" — multiple extraction passes on the same chunk to catch missed entities.
  • 3. Two-Phase Merge
    Extracted nodes and edges are merged into the knowledge graph — entities first, then relationships. Duplicate entities are merged; descriptions are aggregated or LLM-summarized. Source chunk IDs are tracked for provenance.
  • 4. Embedding
    Each entity, each relationship, and each source chunk gets its own vector embedding — stored in the vector database. This enables semantic search at three granularities: entity-level, relationship-level, and chunk-level.

Knowledge Graph Construction

The LLM-driven extraction produces a typed graph where:

Nodes
Typed Entities
Each entity has a name, type (person, organization, concept, technology, etc.), and a merged description aggregated from all chunks that mention it. Duplicates are detected and merged automatically.
Edges
Binary Relationships
Each relationship connects a source entity to a target entity, with keywords (for retrieval), a description (for context), and source chunk IDs (for provenance). Relationships are also embedded for semantic search.
Provenance
Source Tracking
Every entity and relationship tracks which source chunks it was extracted from. At query time, the system can retrieve the original text that supports any graph-derived answer — ensuring citations are always available.
Gleaning: Multi-Pass Extraction

A single LLM pass may miss entities or relationships — especially in dense technical text. LightRAG supports "gleaning": running the extraction prompt multiple times on the same chunk and merging results. This catches entities that one pass overlooked, improving graph completeness without additional source documents.

Query Modes: Local, Global, Hybrid, and Naive

LightRAG's dual-level retrieval system separates queries into two keyword types and routes them through different search paths:

Mode
Local Mode
Embeds low-level keywords (specific entities, names, terms) and queries the entities vector DB. Then traverses the graph from matched entities to collect connected relationships. Best for: precise entity-centric questions.
Mode
Global Mode
Embeds high-level keywords (themes, concepts, patterns) and queries the relationships vector DB. Then collects associated entities. Best for: thematic questions, trend analysis, overview queries.
Mode
Hybrid Mode
Runs both local and global paths plus optionally a direct chunk vector search. Merges results from all paths. Best for: complex questions that need both entity precision and thematic context.
Mode
Naive Mode
Standard vector similarity search over chunks only — no graph traversal. Serves as a baseline comparison and fallback when graph data is unavailable. Equivalent to traditional RAG.
Keyword Decomposition

Before retrieval, the LLM decomposes the user query into two keyword types: high-level (overarching themes like "economic growth", "security architecture") and low-level (specific entities like "Microsoft", "TLS 1.3"). This decomposition drives which retrieval path activates — local searches entity embeddings, global searches relationship embeddings.

Query Flow: End-to-End Example

Here's how a query traverses the system in hybrid mode:

  • 1. Keyword Extraction
    LLM decomposes "How did Company X expand its cloud services?" into low-level keywords ["Company X", "cloud services"] and high-level keywords ["expansion", "growth", "acquisition"].
  • 2. Vector Searches (Parallel)
    Entities VDB → matches ["Company X", "Azure", "GitHub"]. Relationships VDB → matches ["Company X→Azure", "Company X→GitHub"].
  • 3. Graph Traversal
    From "Company X" → finds edges to "Azure", "GitHub", "Office365". From "Company X→Azure" → finds related entities "DataCenters", "AI Services". Multi-hop paths reveal connections not visible in flat search.
  • 4. Chunk Collection
    Source chunk IDs from all matched entities and relationships are gathered. Chunks are scored by weight or vector similarity, deduplicated, and truncated to fit the token budget.
  • 5. Context Assembly
    Entities, relationships, and source chunks are formatted into a structured context string — providing the LLM with both graph-derived structure and supporting text evidence.
  • 6. LLM Generation
    The assembled context is passed to the LLM for final answer generation. The answer benefits from semantic relevance (vector), structural context (graph), and complete source text (chunks).

Storage Architecture: Four Layers

LightRAG uses a pluggable multi-backend storage architecture with four distinct layers:

Layer Purpose Backend Options
Graph Storage Entities, relationships, and their connections NetworkX (default), Neo4j, PostgreSQL, MongoDB, OpenSearch
Vector Storage Embeddings for entities, relationships, and chunks NanoVectorDB (default), FAISS, Milvus, Qdrant, PostgreSQL (pgvector), OpenSearch
Key-Value Storage Chunk text, entity descriptions, metadata JSON files (default), Redis, PostgreSQL, MongoDB, OpenSearch
Document Status Tracking which documents have been ingested JSON files (default), PostgreSQL, MongoDB, OpenSearch
Unified Backend Option

For production deployments, backends like OpenSearch or PostgreSQL can serve as a unified storage layer — handling graph, vector, KV, and document status in a single managed service. This simplifies operations while maintaining the logical separation of concerns.

Caching & Performance

LightRAG implements multi-level caching to optimize both ingestion and query performance:

Ingestion
Document Status Cache
Tracks which documents have already been processed. Re-ingestion skips previously processed documents — only new or modified content triggers extraction. Enables efficient incremental updates.
Query
LLM Response Cache
Caches LLM responses for keyword extraction and answer generation. Identical queries return cached results without re-invoking the LLM — significantly reducing latency and cost for repeated questions.
Graph
Entity Merge Cache
During ingestion, entity deduplication and merge results are cached. When the same entity is encountered in new documents, the system merges descriptions without reprocessing the entire graph.

Multimodal Support

LightRAG extends beyond text through integration with multimodal processing pipelines (e.g., RAG-Anything). This enables knowledge graph construction from:

Source
Images & Diagrams
Vision-Language Models (VLMs) extract descriptions from images, architecture diagrams, and flowcharts — converting visual information into text that feeds the entity extraction pipeline.
Source
Tables & Structured Data
Tabular data is parsed and converted into entity-relationship triples. Column headers become entity types; rows become instances. Relationships between table entities are inferred and added to the graph.

Practical Limitations & Tradeoffs

LightRAG is powerful but not without cost. From hands-on experience, here are the real tradeoffs teams should plan for:

Cost
Graph Construction is Expensive
Entity and relationship extraction requires an LLM call for every chunk — often with multiple "gleaning" passes. For large document sets, initial graph construction can take hours and consume significant LLM tokens. However, incremental updates are supported — new documents get processed without rebuilding the entire graph.
Tuning
Parameter Sensitivity
The number of entities, relationships, and chunks to retrieve must be carefully tuned per use case. Too many results overload the LLM context window with irrelevant information, degrading answer quality. Too few miss critical context. Finding the right balance requires experimentation with your specific data and query patterns.
Latency
Slower Answer Generation
Compared to standard vector RAG, LightRAG adds latency: keyword extraction (LLM call), dual vector searches, graph traversal, chunk collection, and context assembly — all before the final generation call. Total query time is noticeably higher than a simple similarity search + generate pattern.
Quality
Extraction Quality Depends on the LLM
The knowledge graph is only as good as the LLM's extraction capability. Weaker models miss entities, invent relationships, or produce inconsistent typing. Using a capable model for extraction (even if you use a smaller model for query-time generation) is critical for graph quality.
Scale
Graph Growth Management
As the graph grows, entity merging becomes complex — duplicate detection across thousands of entities requires LLM-based summarization, adding cost. Graph traversal time also increases with edge count. Production deployments need a strategy for graph pruning or partitioning.
Debugging
Harder to Debug Than Standard RAG
When answers are wrong, the failure could be in extraction (bad entities), graph structure (missing edges), vector search (wrong matches), chunk selection (wrong source text), or generation. Multiple retrieval paths make root-cause analysis more complex than single-path vector RAG.

The Incremental Update Advantage

Despite the high initial cost, LightRAG's incremental update capability is a significant operational benefit. When new documents arrive, only those documents are processed — new entities merge into the existing graph, new relationships extend it. You don't restart from scratch. This makes the upfront investment amortizable over time.

When to Use LightRAG

Good Fit
Documents with Rich Entity Relationships
Technical documentation, specifications, research papers — anywhere entities reference, depend on, or conflict with each other across documents.
Good Fit
Multi-Hop Questions
"What depends on X?" "If Y changes, what's affected?" — questions requiring traversal of relationships that standard search cannot answer.
Good Fit
Thematic Exploration
"What are the main trends in X?" "How does Y relate to Z at a high level?" — questions needing aggregation across many documents.
Less Ideal
Simple Factual Lookup
If your questions are always simple and self-contained within a single chunk, the overhead of graph construction may not justify the benefit. Standard vector RAG suffices.
The Takeaway

LightRAG shines when your documents contain interconnected knowledge — where understanding the relationships between entities is as important as finding the entities themselves. It's the middle ground between simple vector RAG (fast, flat) and full enterprise knowledge graphs (complex, manual) — automated graph construction with retrieval that leverages structure.
